# ADR-020: A dedicated RLS policy for the email log, with an optional tenant

- **Status**: Accepted
- **Date**: 2026-09-19
- **Deciders**: project owner
- **Related**: [[ADR-003]], [[ADR-009]], [[ADR-014]], [[ADR-016]]

## Context and problem statement

`Database\Migrations\Concerns\EnablesRowLevelSecurity::enableRlsWithPolicy()` carries an explicit rule in its docblock: "A single caller in the whole application: `memberships` ([[ADR-014]], point 2). Any second caller needs an ADR, not a commit." The `sent_emails` table (BR-DEMO-02, specs §22.3, Phase 4) is that second caller. This ADR is the condition the rule imposes.

The rule exists for a measured reason, not out of formalism: the uniform policy generated by `enableRls()` is the only form verified both for isolation ([[ADR-014]]) and for query plan ([[ADR-016]] — cast on the setting, not on the column, otherwise a `Seq Scan` over 50,000 rows replaces an `Index Scan`). Every hand-written policy is a new surface where both guarantees can be lost silently, without any functional test noticing.

**The concrete problem:** BR-DEMO-02 requires *every* transactional email to be logged — and it explicitly lists "member invitations, scheduled reports, **password reset**". The first two have a tenant: they start from a job or a request already inside a workspace context. **Password reset does not.** `PasswordResetLinkController` sits on `guest` routes, outside the `session.context` and `workspace` groups (`routes/web.php`) — there is no tenant to attribute at the moment of sending. So `sent_emails.tenant_id` has to be nullable, and the uniform policy does not cover tenant-less rows.

## Decision drivers

- **The requirement is explicit in the specification**, not inferred: password reset is named in so many words in BR-DEMO-02.
- **No INSERT that fails silently.** RLS policies only have `USING`, and PostgreSQL applies it **as `WITH CHECK` as well** (`.ai/rules/tenancy.md`). A policy that does not account for the "no tenant" case does not merely hide the row — it rejects the write.
- **Zero cross-tenant leakage**, a condition that is not negotiable ([[ADR-003]]).
- **No write-once-read-never rows.** The log contains full email bodies, hence personal data: retention (§20.5) has to be able to delete it too, not just write it.
- **The indexable form from [[ADR-016]]** is preserved on the branch that matters for volume.

## Considered options

1. **`tenant_id` NOT NULL, no logging for tenant-less email.** The simplest: the uniform policy stays the only one in the project, the trait's rule is untouched. **Rejected** — it directly contradicts the letter of BR-DEMO-02, which requires password reset in the log. It would have meant cutting a requirement in order to preserve a convention.
2. **`tenant_id` nullable, with the uniform `enableRls()` policy.** **Rejected, and it is the most instructive case:** the uniform policy is `tenant_id = current_setting('app.tenant_id', true)::bpchar`. A comparison with `NULL` yields `NULL`, so the row would be invisible on read — which seems acceptable. But PostgreSQL applies the same expression on INSERT: a row with `tenant_id = NULL` yields `NULL` at check time, and the write is rejected with "new row violates row-level security policy". Logging of password resets would not have been incomplete — it would have been an error in the sending flow.
3. **`tenant_id` nullable, with an explicit second branch for "no context at all".** **Chosen.**

## Decision

`sent_emails` gets its own policy, named `sent_email_visibility`:

```sql
(tenant_id = current_setting('app.tenant_id', true)::bpchar)
OR (tenant_id IS NULL AND coalesce(current_setting('app.tenant_id', true), '') = '')
```

The first branch is generated by `matchesSetting()`, so the indexable form from [[ADR-016]] stays unchanged where it matters for volume (the index is `(tenant_id, created_at)`). The second branch applies exclusively to tenant-less rows.

**Why `coalesce(…, '') = ''` and not `IS NULL`.** `current_setting('app.tenant_id', true)` returns `NULL` only on a connection that has **never** called `set_config` for that variable. Once a previous transaction has emptied it, it returns `''`, not `NULL` (behaviour verified in [[ADR-016]]). The Horizon queue worker is a long-lived process that reuses the same connection across jobs belonging to different tenants — so it reaches `''` right after the first tenant job, not the virgin state. With a strict `IS NULL`, the second branch would have been effectively dead on any connection that had ever seen a tenant: exactly the silent-bug pattern `.ai/rules/tenancy.md` documents under "Per-request memoization". `coalesce(…, '') = ''` treats `NULL` and `''` identically, consistently with the rest of the policies ("missing setting → zero rows; empty setting → zero rows. It all fails closed.").

**Why the second branch is not optional.** Without it, the tenant-less rows would have been write-once-read-never: no query, from any context, could have read them or deleted them at retention time (`PruneSentEmailsJob`). They would have stayed in the table forever, with full email bodies — the opposite of the minimization requirement in §20.5.

## Verification

The behaviour is **measured with two real `psql` sessions**, as `throughput_app` (the role without `BYPASSRLS`), not inferred from reading the policy:

| Context | Observed result | Expected |
|---|---|---|
| `app.tenant_id` = a ULID | sees only that tenant's rows; the tenant-less row is invisible | yes |
| `app.tenant_id` = `''` (the Horizon worker between jobs) | sees only the tenant-less rows | yes |
| INSERT with `tenant_id = NULL` under a tenant context | `ERROR: new row violates row-level security policy` | yes |

The third row is the important one: an active tenant cannot even *write* a tenant-less row, so the second branch cannot be used as a back door for hiding data from that tenant.

## Consequences

**Positive**

- BR-DEMO-02 is covered in full, password reset flow included.
- Cross-tenant isolation stays total, verified empirically (the table above) and covered by
  tests: `SentEmailsTest::test_a_tenant_never_sees_another_tenants_sent_emails` and
  `::test_a_tenant_less_row_never_appears_in_any_workspace`, plus the generic structural guard
  `IsolationTest::test_every_table_with_a_tenant_id_column_has_row_level_security_enabled`,
  which automatically catches any table with a `tenant_id`, this one included.
- Retention can delete tenant-less rows as well.
- The indexable form from [[ADR-016]] is preserved on the branch that carries the volume.

**Negative, accepted**

- The second hand-written policy in the project. The "a second caller needs an ADR" rule stays in force; **a third caller needs a new ADR**, not a reference to this one.
- Tenant-less rows are not visible on any workspace screen, by construction. They are reachable only by code running without a context (the retention job). If an operations screen for them becomes necessary, that requires a separate decision — it is not solved by weakening the policy.
- **A known gap, documented, not closed by this ADR:** an email sent from a job that has already closed its tenant context before the external call (as [[ADR-013]] requires) lands in the log with `tenant_id = NULL`, hence invisible in the Settings of the tenant that triggered it. Correct attribution requires the job to pass the tenant explicitly along with the message; the mechanism exists (the `X-Throughput-Tenant-Id` header, read and stripped by `DemoInterceptingTransport`), but each sender has to set it.
